# BluePulse Stage1 完成门槛与 Stage2 总路线

> 本文是 BluePulse 当前主线前端与已合并后端的统一路线文档。它先审计 Stage1 的真实完成度，再定义支撑现有前端的补完工作，最后进入事件、项目、证据和可信度能力。

## 1. 范围与阶段原则

BluePulse 当前是一个新闻采集、处理和呈现平台。“新闻推送”在本文中仅指来源采集、内容处理、精选生成和前端展示，不包含订阅、站外通知、邮件或其他用户运营能力。

后续stage3会在前端方面添加新的功能，暂时后端不用考虑。

这篇md文档主要是stage1对你目中除去前push在分支上的内容以外的其他功能的重新清洗整合，你现在可以抛弃stage1了，直接以这份文档为主，这篇stage2本质上就是stage1的一部分+stage2新的部分

Stage1 的完成门槛不是“接口能返回文章”，而是：公开来源能够稳定进入处理流水线，文章在字段缺失或单来源失败时仍可保留，前端可以查看真实原文和可用媒体，并能按主题、来源、时间、关键词和实体进行可解释筛选。只有达到这个门槛，Stage2 才开始做跨文章知识组织。

## 2. 当前 Stage1 完成度审计

### 2.1 已具备

- FastAPI、SQLite 本地配置、PostgreSQL 兼容配置和 Alembic 迁移。
- GDELT、Police1 RSS、OpenAlex 采集适配器及受控来源配置。
- canonical URL 去重、内容指纹和重复候选标记。
- Article、Source、Media、FeaturedSnapshot、IngestionRun 等基础模型。
- `/api/v1/home/featured`、`/api/v1/articles`、`/api/v1/articles/{id}`、`/api/v1/taxonomy`、`/api/v1/sources`。
- 前端同源 API 代理、精选、列表、详情、搜索、主题/来源/地区/时间/排序筛选、cursor 分页和 mock 开关。
- 每日 `Asia/Shanghai 06:00` worker 的基础调度与精选快照流程。

### 2.2 尚未达到完成门槛

1. **模型处理**：缺少供应商无关的结构化 adapter，尚未稳定生成中文标题、中文摘要、正文译文、关键词、主题建议和重要性评分。
2. **正文抓取**：GDELT 主要保存元数据；RSS 主要保存 feed 摘要；缺少通用公开页面正文解析、清洗、长度上限和失败状态。
3. **媒体提取**：Media 模型存在，但图片、视频、音频和附件的 MIME、尺寸、alt、说明、缩略图及解析状态尚未完整写入流水线。
4. **实体目录**：缺少厂商、模型、机构实体目录、Article-Entity 关系及实体筛选 API。
5. **重复关系**：当前只有 `duplicate_candidate` 状态，尚缺少表达原文、转载、翻译和相似报道的 DuplicateLink 关系。
6. **管理与运行控制**：缺少管理员 session/CSRF、软删除/恢复、审计日志、运行查询、手动补跑、失败重试、任务锁、幂等键和租约恢复。
7. **评论和内容状态**：详情应明确返回评论不可用、正文缺失、媒体缺失和模型失败等状态，而不是让前端推断。
8. **验证交付**：后端自动化测试、OpenAPI 校验、配置示例、PostgreSQL 实机验证和可重复 smoke test 尚不完整。

## 3. Stage1 补完清单

### 3.1 供应商无关的模型适配层

定义只负责输入输出、不直接写数据库的 `ModelAdapter` 接口。运行时由环境配置选择供应商、模型名、超时、预算和密钥；测试使用确定性的离线替身。

结构化结果至少包含：

- 中文标题、中文摘要和可选正文译文。
- 关键词数组：规范化文本、语言、置信度和排序。
- 主题建议：候选 taxonomy、置信度和理由。
- 重要性评分：固定区间数值、评分依据和模型版本。
- 实体候选：厂商、模型、机构及置信度。
- 处理状态、重试次数、错误类别和模型版本。

模型超时、限流、无效 JSON 或供应商不可用时，不丢弃文章；保留原始内容并标记 `pending_model` 或 `model_failed`。

### 3.2 正文与媒体采集

- GDELT 页面和 RSS 页面均支持公开正文提取、HTML 清洗、脚本/样式剔除、正文长度上限和解析失败原因。
- 仅访问来源清单允许的 HTTP(S) 目标，遵守 robots、条款、User-Agent、请求频率、超时和响应体上限。
- 不绕过登录、付费墙、验证码或强反爬；公开正文不可得时保留摘要和真实原文链接。
- 抽取图片、视频、音频和附件元信息：类型、MIME、尺寸、来源 URL、缩略图 URL、说明、alt、顺序和状态。
- 单个正文或媒体失败不能阻塞文章入库；媒体默认保存元数据和链接，不强制镜像二进制。

### 3.3 实体和重复关系

- 建立 Vendor、Model、Organization 等实体目录及规范名称、别名、语言和状态。
- 建立 Article-Entity 关系，记录关系类型和来源（规则、模型或人工）。
- 建立 DuplicateLink，至少支持 `original`、`republished`、`translated`、`similar`，并保存置信度和判定依据。

### 3.4 管理与 worker 可靠性

- 管理员登录、session、CSRF、最小权限、软删除/恢复和审计日志。
- `/admin/ingestion-runs`、`/admin/ingestion-runs/{id}`、手动补跑和失败重试。
- 任务锁、幂等键、租约过期恢复、来源级状态和阶段级统计。
- 统一错误格式、稳定枚举、可重复迁移和配置模板。

## 4. 前后端真实接入契约

### 4.0 当前前端接入面

- `HomeDashboard` 是精选、列表、详情、搜索、筛选、cursor 分页、浏览历史和移动端入口的统一消费方。
- `BranchedTopicMenu` 的固定三组七主题菜单继续由 taxonomy 接口提供主题标签；父级菜单不改为可折叠交互。
- `src/app/_lib/home-data.ts` 负责前端数据映射和 mock/真实数据边界；生产路径不自动混入 mock，只有显式 `?mock=1` 才启用 mock。
- `src/app/api/bluepulse/[...path]/route.ts` 继续作为同源代理，统一转发公开 API 和错误响应。
- 精选槽位 `p0`–`p5` 与后端精选快照保持稳定对应；不足六篇时返回实际数量。
- 详情页按“中文内容 → 原文内容 → 媒体 → 来源 → 真实原文链接 → 缺失状态”顺序展示，不把不可获取正文或媒体伪装成已完成内容。

### 4.1 首页、列表和目录

稳定公开接口：

- `GET /api/v1/home/featured`
- `GET /api/v1/articles`
- `GET /api/v1/articles/{id}`
- `GET /api/v1/taxonomy`
- `GET /api/v1/sources`
- `GET /api/v1/entities`（Stage1 补完）
- `GET /api/v1/entities/{id}`（Stage1 补完）

`/articles` 统一支持：

`q`、`topic`、`region`、`source`、`source_type`、`entity`、`published_from`、`published_to`、`sort`、`cursor`、`limit`。

响应必须包含稳定的分页结构、过滤条件回显、来源信息、内容状态和统一错误码。cursor 不依赖客户端猜测时间或 ID，排序变化时必须返回新的 cursor。

### 4.2 文章详情

详情响应统一提供：

- 中文标题、原始标题、中文摘要和原文摘要。
- 中文正文、原文正文、正文语言和正文状态。
- 关键词、主题、地区、实体和重要性评分。
- 来源、来源类型、作者、发布时间、首次发现时间和采集时间。
- canonical URL 和真实原文链接。
- 图片、视频、音频、附件媒体数组及媒体状态。
- 翻译/模型处理状态、版本和失败原因。
- 重复/转载/翻译关系。
- `comments.available=false` 等明确的评论能力状态。

正文、翻译或媒体缺失时返回明确状态，不生成伪造内容；前端继续显示摘要、缺失提示和原站链接。

### 4.3 搜索和语义筛选

本阶段只做站内搜索，不接外部实时搜索。搜索覆盖中文标题、原始标题、中文摘要、正文、原文正文、关键词、实体名称和来源名称。

SQLite 使用 FTS5，PostgreSQL 使用对应全文检索能力；API 保持一致的查询、排序、分页和高亮/匹配字段。早期可用 SQL `LIKE` 作为降级路径，但生产验收必须有全文索引。

语义筛选由基础 taxonomy、实体、关键词、重要性和内容状态组合构成。模型建议必须保留置信度和理由，最终分类必须可解释。

## 5. Stage2：事件、项目与证据体系

Stage2 在 Stage1 完成门槛通过后启动，重点从“文章可读”升级为“事实可追溯、来源可比较”。

### 5.1 事件归并

- 建立 Event 模型、状态和事件详情 API。
- 使用 canonical URL、内容指纹、时间窗口、实体重合和语义相似度生成候选归并。
- 支持确认、拆分、合并和撤销归并，并保留操作记录。
- 事件详情展示相关文章、媒体、来源分布和归并依据。

### 5.2 项目档案

- 建立 Project 模型及项目详情 API。
- 关联机构、厂商、模型、事件和文章。
- 保存项目状态、首次发现时间、最近更新时间和来源覆盖度。
- 支持从文章、事件和实体反向进入项目档案。

### 5.3 时间线

- 建立 EventTimelineEntry。
- 同时保留来源发布时间、平台发现时间和采集时间。
- 支持文章、声明、证据和状态变化作为时间线节点。
- 时间线排序必须有明确的时间字段和稳定的并列排序规则。

### 5.4 Claim / Evidence

- Claim 保存主张文本、提出方、时间、关联事件/项目和状态。
- Evidence 保存文章段落、媒体、原始链接或其他可定位证据。
- Claim-Evidence 关系支持支持、反驳和部分支持。
- 保存引用片段、定位信息和原文链接，确保可回溯。

### 5.5 交叉验证与可信度

- 计算来源独立性、来源类型、发布时间和重复关系。
- 展示交叉验证覆盖度、独立来源数量和最后验证时间。
- 冲突主张并列展示，不强行合并。
- 可信度必须返回可解释因素，而不是只返回黑盒分数。

## 6. API、数据库与兼容原则

- 新增字段保持向后兼容；旧文章允许 `pending_model`、`summary_only`、`media_unavailable` 等状态。
- 公开接口使用统一错误格式和稳定枚举。
- canonical URL、内容指纹和外部来源 ID 建立唯一约束；迁移必须可重复执行并提供回滚路径。
- 抓取或模型失败不得破坏已入库文章。
- Stage1 不提前构建空壳的知识图谱、Trend、Report、Alert、订阅或通知服务。

## 7. 测试、验收与发布门槛

### 7.1 Stage1 验收

- 采集、URL 规范化、去重、正文解析、媒体提取和模型 adapter 单元测试。
- 首页、列表、详情、搜索、主题、来源和实体 API 集成测试。
- SQLite 与 PostgreSQL 迁移、查询和全文索引验证。
- 失败重试、幂等、任务锁、租约恢复和重复运行测试。
- 前端验证桌面视口、移动视口、reduced-motion、真实后端、正文/媒体缺失、搜索、筛选和 cursor 分页。
- 至少完成一次可重复的端到端 smoke test：采集 → 入库 → 精选 → 列表 → 详情 → 原文链接。

### 7.2 Stage2 验收

- 事件候选生成、确认、拆分、合并和撤销测试。
- 项目档案和时间线排序测试。
- Claim/Evidence 引用完整性和原文回溯测试。
- 冲突检测、来源独立性和可信度解释测试。
- 从文章详情可以追溯到原始链接、媒体、事件、项目和证据。

## 8. 假设与非目标

- 本文文件名为 `docs/stage2-plan.md`。
- 模型采用供应商无关适配层，供应商通过环境配置选择，测试使用离线确定性替身。
- 搜索只覆盖已采集入库的 BluePulse 内容。
- “新闻推送”不包含订阅、通知、邮件、站外推送或用户运营。
- 不绕过登录、付费墙、验证码或反爬限制。
- 保持 Next.js 16、React 19、TypeScript、Tailwind CSS 4、GSAP 3 现有技术栈。
