## 1. 目标与边界

BluePulse 首先要稳定完成一条闭环：公开来源 → 受控采集 → 原文与媒体元信息 → 相关性判断 → 中文整理与分类 → 全部动态 / 精选 → 搜索、详情与原站追溯。相关不等于值得精选；报道某项试点也不等于证明其效果。

- 运行环境以 Windows 为主，沿用当前 Next.js 前端、FastAPI API、Python worker 和本地 SQLite。Python 版本按可用环境与依赖兼容性确定。PostgreSQL 在 Stage1 验收时实测迁移与查询；不为借鉴 AIHOT 而换栈。
- 来源仅限配置允许的公开 HTTP(S) 目标；遵守 robots、条款、请求频率和响应上限。不绕过登录、验证码、付费墙或访问挑战。站内公开全文遵守来源许可；默认可展示摘要、来源信息和真实原文链接。
- 模型是受控的文本处理组件。采集、去重、任务调度、发布状态、权限和审计由确定性程序控制。模型不得根据常识补写原文没有的金额、效果或机构关系。
- Stage1 完成门槛沿用现有 `stage2-plan.md`：稳定采集、缺失回退、可用媒体、解释性筛选、可靠运行和验收。事件、项目、Claim/Evidence 在该门槛通过后进入 Stage2。
- 本轮不建设普通用户、订阅、站外推送、日报/周报、趋势热度或 MCP。现有文档里的“新闻推送”仍只指平台内部处理与展示。

## 3. 产品判定标准：先确定“有用”

### 3.1 相关性与公开状态

预筛分四类：`direct`（科技在警务中的具体运用、建设、研究或直接治理此类技术的政策）、`potential`（没有警务字样，但有具体新能力及合理警务应用路径的重要上游技术、模型或治理进展）、`irrelevant`（无上述实质关联）和 `uncertain`（证据不足）。七类 taxonomy 保持不变，但只是相关内容的主题分类，不构成七种自动入选条件；大模型、智能体、无人机是重点方向而非排他性三类。常规枪支弹药、防弹衣及其普通性能标准不因“警用装备/政策”而入选；跨年专利清单也不因含技术名词自动入选。确有新型智能技术及明确警务用途的装备仍逐案判断。警务信息系统的常规运维可以相关但通常不精选；算法监控与隐私治理议题可以相关，但非重点地区的比较法讨论、无新实施规则时通常不精选。`potential` 必须保存原文的新信息及其影响路径；“任何 AI 都可能用于警务”不能成为入库理由。

相关且低分的文章进入“全部动态”，不自动进入精选。`irrelevant` 保留内部判定记录，不公开；`uncertain` 与模型失败保留原始记录和待处理状态，在完成可靠回退或人工确认前不自动公开。相关性、正文可用性、模型状态、可见性、精选入选分别记录，不能复用一个 `processing_status` 表达全部含义。

### 3.2 固定主题与补充标签

七个既有 taxonomy slug 和前端三组菜单保持稳定。每篇文章有一个主主题，可有多个次主题；另存以下**独立维度**：

- 内容类型：技术研究、产品装备、落地案例、政策标准、行业动态。采购/招标可以作为内容类型的受控补充值，或保留在现有“采购与项目”主题中；确定枚举前先看样本，不能直接改现有主题 URL。
- 业务标签：例如交通管理、反诈、刑事勘查、巡防、应急。
- 技术标签：例如无人机、视频分析、音频鉴伪、大模型。
- 阶段标签：研究、发布、招标、试点、部署、评估等。

标签来自版本化受控词表。模型返回词表之外的候选时，记录待审候选，不自动制造新公开标签。厂商、模型、机构继续走实体目录；文章—实体关系补充关系类型、来源（规则/模型/人工）和证据字段。名称命中只是提及关系，不推断采购、合作或使用关系。

### 3.3 价值评分与精选

先用一套可解释的 0–100 分试行量表：具体警务任务关联 30 分、信息增量 25 分、证据强度 25 分、实践可用性 20 分。新近程度独立用于排序，不混进文章的固有价值分。评分结果保存分项、总分、理由、证据定位、模型与规则版本。

精选须同时满足：相关、内容可用、达到经样本校准的门槛、没有未解决的重大事实/重复问题。官方一手、媒体、论文可有不同门槛，但须先用 BluePulse 样本校准；既有 `trust_level` 不直接映射 AIHOT 的 T1/T2 数字。官方来源提高“确实发布过”的证据强度，不自动证明产品效果。首页最多六条，候选不足就返回实际数量；同一事件的转载原则上不占多个槽位。

对每篇精选分别保存“原文事实摘要”和“为何值得关注的分析判断”。前端明确区分这两种文字。首版先做一次结构化分析；只有错例与预算数据说明有必要时，再引入双次评分或第二模型。

### 3.4 标注与评测

从五类现有来源和计划新增来源选 100–150 条去标识化样本，含采购公告、会议宣传、厂商案例、政府试点、技术论文、转载、旧文和正文缺失。每条人工标注相关性、是否精选、主主题/内容类型、证据级别与简短理由；至少 20% 留作不参与调参的保留集。测试样本不记录账号密钥或不必要的个人信息。

评测分别报告相关性漏选、精选误选、主题/实体错误和事实性摘要错误；按来源类型和难例分组看错例。门槛根据标注结果确定并写入配置，不把 AIHOT 的 60/65/76 当默认值。每次规则或提示词变更保留版本和评测报告；未经人工检查的单一准确率不能作为发布结论。

## 4. 实施阶段与完成条件

### P0：固定可继续开发的基线

**依赖：无。** 核对远端首页与本地文章/实体页、采集器、迁移及 README 的集成状态；确认开发库、密钥、构建产物被忽略；明确旧 `featured` 辅助逻辑与新版首页之间谁是实际消费方。形成当前路由、配置、数据库迁移、现有测试及已知失败的清单。

**完成条件：** 本地代码能按 Windows 启动说明跑通 API 与前端；工作区改动有可恢复记录；后续任务不再建立在未说明的冲突或误判现状上。

### P1：样本、判定规则与内容数据契约

**依赖：P0。** 完成 3.4 的标注集；把预筛、价值评分、事实摘要、推荐理由分别写成版本化规则；确定七主题外的内容类型和标签词表。新增迁移与结构化结果：主/次主题、标签、关键词、相关性类别/理由、评分分项/理由、模型及提示词版本、处理错误类别、可见性、精选决策。旧文章缺值时标记 `unknown` 或待处理，不编造历史模型结果。

模型层定义输入/输出稳定的 `ModelAdapter`，先封装现有兼容接口实现，并提供离线确定性替身。短文分析可合并为一次调用；长正文翻译保持独立分块。调用结果按输入内容指纹、任务、模型和提示词版本复用；配置单次、每日或运行级预算，超限时保留文章并标明原因。

**完成条件：** 宽预筛不再只因缺少“公安/警察”等字样丢弃可解释的 `potential`；同一内容和同一版本重试不重复计费；模型失败可重试且不损坏原文；样本评测能复现每次精选决策。

### P2：正文、媒体与来源可靠性

**依赖：P0，可与 P1 的样本工作并行。** 对 GDELT 和 RSS 的原站页面建立来源级允许主机/路径策略；不能因 GDELT 返回任意链接就自动访问任意站点。实现通用 HTML 清洗与正文长度/失败状态，保留 CCGP、NIJ 的站点专用规则。Police1 等来源遇到访问挑战时记录失败，保留摘要和原站链接。

提取图片、视频、音频与附件的可用元信息及状态；媒体失败不阻断文章。增加来源采集位置、最近成功/错误、失败不推进位置、每来源固定频率和手动补跑。区分原站发布时间、首次发现与最近抓取；缺发布时间或历史回灌不进入“今日”候选。canonical URL 不变但正文确实变化时记录内容版本并避免重复模型调用。

**完成条件：** 可访问来源在代表性页面上提取正文与媒体；失败页面仍有真实链接和明确回退；单来源失败不影响其他来源；重复运行既不重复入库，也不把旧文刷新成今日新闻。

### P3：精选、检索与前端阅读闭环

**依赖：P1、P2 的公开内容契约。** 先建立 Stage1 所需的 `DuplicateLink`，记录原文、转载、翻译和相似报道及判定依据。精选快照在现有“24 小时优先、7 天补足”窗口内应用入选门槛、来源多样性和重复关系，保存决策/规则版本及推荐理由；无足够候选时不补占位新闻。全部动态按真实发表时间浏览，相关低分文章仍可查。公开 API 补 `published_from/to`、条件回显、关键词/实体筛选、实体详情、内容/媒体/翻译状态和统一错误格式；SQLite 用 FTS5，PostgreSQL 验证对应全文检索实现。

前端继续使用当前 `HomeDashboard`、同源代理和七主题菜单，不重做视觉样式。首页展示精选理由，列表与详情展示原始/中文内容、证据状态和真实原站链接；对缺正文、缺媒体、缺译文、日期未知给出一致提示。确认 `?mock=1` 才使用 mock。公开全文是否展示由来源级许可配置决定。

**完成条件：** 从采集入库的真实文章可经过首页精选或全部动态到达详情和原站；筛选、排序、分页不因状态变化产生重复/漏页；桌面、移动及 reduced-motion 路径都可使用。

### P4：worker、最小管理能力与 Stage1 验收

**依赖：P1–P3 主链路。** 为同来源并发运行增加任务锁、幂等键和过期租约恢复；运行记录可按来源、时间和状态查询，可按权限补跑失败来源；来源健康和阶段计数可见。管理员登录、session/CSRF、软删除/恢复和审计属于既有 Stage1 完成门槛，安排在内容主链路稳定之后。来源增删改仍可先通过受控配置完成，不在此阶段建设复杂来源后台。

以离线 fixture 验证适配器、模型、分页、去重、媒体及状态回退；分别实测 SQLite/PostgreSQL 迁移与查询；做一条可重复的“采集 → 入库 → 精选/全部动态 → 详情 → 原站” smoke。对公网不可达或受访问挑战的来源，明确记录限制，不以绕过挑战作为验收条件。Windows 启动、停机和每日调度说明可由另一台同类环境复现。

**Stage1 通过条件：** `stage2-plan.md` 第 7.1 节的验收项逐项有结果；本节所列关键失败场景有测试或可复现记录；采集失败、模型失败或正文缺失不会产生虚构内容或丢失已入库文章。若管理员功能继续暂缓，需明确标记“Stage1 内容闭环可试用，Stage1 整体验收未完成”。

## 5. Stage2：先事件，后项目与证据

### S1：事件候选和关系判断

复用 Stage1 的 `DuplicateLink` 作为文章关系依据，但不把文章关系直接当成事件。建立 Event、ArticleEvent 和人工覆盖记录。先用时间窗口、实体、地点、标题/摘要与内容指纹召回少量候选，再判断 `same_occurrence`（同一次）、`follow_up`（直接进展）、`unrelated`、`roundup`（汇总）。同设备、同厂商或同主题不能单独构成同一事件。

管理员能确认、拆分、合并、撤销，人工决定优先且自动任务不能覆盖。文章详情显示事件内来源及后续进展，保留独立原文链接。先标注一小批难例关系对，报告误合并和漏合并；误合并优先处理。

### S2：项目档案和时间线

在事件关系稳定后建立 Project 和 EventTimelineEntry，链接机构、厂商、模型、文章与事件。时间线分别保存来源发表、平台发现、采集与事件发生时间；不把发表时间误当发生时间。支持从文章和实体反向进入项目，记录状态变化来源。

### S3：Claim / Evidence 与交叉验证

主张、提出方、时间、原文片段和可定位证据分开存储；证据关系支持支持、反驳、部分支持。来源独立性计算需考虑转载、翻译与同集团发布，不能按 URL 数量冒充独立证据。矛盾主张并列呈现，可信度展示可解释因素和最后核验时间。

**Stage2 通过条件：** 能从一条文章追到原站、同事件报道、项目及其证据；同一试点的官宣/转载会正确相连，一个月后的评估作为进展，另一地区同类采购保持独立；人工修正重跑后仍有效。其余验收沿用 `stage2-plan.md` 第 7.2 节。
